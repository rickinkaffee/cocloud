# Enterprise WeChat desktop gateway (optional)

Independent of `/wechat/`. The gateway proxies an operator-supplied noVNC desktop; it does not install the official Linux client, perform account sign-in, or read profiles, windows, databases, contacts, messages, or QR codes to determine status. An authorized desktop viewer can see and control everything shown on that desktop.

1. Run the official enterprise client (installed by the operator) under a dedicated Unix user in an isolated VM/container or private network namespace. Use a dedicated display with X authentication, no TCP X listener, and a separate persistent home. Never attach the personal WeChat display. Start the client in that session and configure the session supervisor to restart it. Do not publish raw VNC, websockify, or desktop TCP ports, even on host loopback if other host users are untrusted.
2. Provide a private HTTP Unix socket serving the noVNC distribution (`/vnc.html`, `/app/`, `/core/`, `/vendor/`) and `/websockify` upgrades. For example, inside the isolated namespace run `websockify --web /usr/share/novnc 127.0.0.1:6081 127.0.0.1:5901` against the dedicated password-protected VNC display, then `socat UNIX-LISTEN:/run/wecom-desktop/http.sock,fork,mode=0660 TCP:127.0.0.1:6081`. Share only the socket directory with the gateway. Provision the directory as trusted desktop owner, group `wecom-desktop-gateway`, mode `2750`; only the gateway may join that group. Keep file creation group ownership consistent and restrict access to the socket on restart. Do not expose any alternate proxy location for the underlying desktop.
3. Build with `python3 extensions/wecom/build.py /new/release/path` from the candidate. Install the emitted `wecom` directory under `/opt/workbench/extensions/`. Copy `wecom.env.example` to `/etc/workbench/wecom.env` (root-owned, `0600`), set the HTTPS origin and a random admin secret. Install the systemd unit; ensure Node 24+ is in the service PATH or pin an absolute Node executable. Import `wecom.caddy` inside the existing HTTPS workbench site before its catch-all handler. Keep default port or update both files. Validate the merged Caddy configuration before reloading it. Enable the gateway with `systemctl enable --now wecom-gateway`. Do not enable on a workbench where untrusted users can run host commands, edit the gateway, or read its secrets. Keep request credential logging disabled.
4. Authenticate to the workbench in a trusted browser, open `/wecom/`, then enter HTTP Basic user `admin` and the dedicated secret. The session must also have `environment:maintain`. Every desktop asset and WebSocket requires both checks. Open sockets are checked every 30 seconds; stop/restart the gateway for immediate disconnection or secret rotation. Close the trusted browser profile after use. Complete any QR approval directly in the official client.

`GET /wecom/api/status` requires a valid workbench browser cookie, not the admin password. It returns only `{state,detail}`. Missing desktop socket means `offline` (unreachable here, not proof the account signed out). A reachable noVNC page does **not** establish login: without a fresh attestation return `error`. A trusted operator or separately vetted source can atomically write exactly `online` or `offline` (optional newline) to `login.state` after checking login. Use regular files mode `0640`, not symlinks, in the protected directory. Reports expire after 60 seconds; never refresh blindly. No automatic official login detector is included. HTTP 401/403 means access denied; 503 means auth/service unavailable. To accept a real installation verify auth denial, sign-in and disconnect on that isolated display, and separately verify status reporting. No live credentials are needed for the build tests.
